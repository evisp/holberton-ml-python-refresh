Project 3

Data pipelines – from messy JSON to clean CSV

In this project you build a small, script-based pipeline over real brewery data — missing coordinates, phone numbers in four different formats, commas inside addresses, accented names. You will separate the work into extract, transform, and load steps, and decide for yourself what "clean" means.

📄 JSON input 📑 CSV output ⚙️ Extract–Transform–Load 🧹 Real cleaning decisions
Focus: cleaning data that fights back Pattern: extract → transform → load Data: Open Brewery DB Prerequisite: Week 3 tutorial

Key concepts

  • Separating data work into extract, transform, and load steps.
  • Inspecting raw data before writing any code against it.
  • Normalizing inconsistent values and handling missing fields.
  • Using csv.DictWriter to write a file with an explicit schema.
  • Designing functions that take data in and return data out, without doing I/O.

Study first (15–30 minutes)

  • Start here: the Week 3 pipelines tutorial — it covers this whole project from the ground up.
  • Python docs: json module (json.load, json.dump).
  • Python docs: csv module, especially csv.DictWriter.
  • A brief overview of "ETL" as reading, cleaning, and writing data.

The pipeline is small on purpose. The data is not tidy on purpose. The pattern you practice here is the one you will use on far larger datasets.

Download the raw input file

This project uses a new dataset. Unlike the todos from Project 2, this one is real, community-maintained, and full of gaps.

Open Brewery DB

Open Brewery DB is a free, open dataset of breweries, cideries, brewpubs and bottleshops around the world. No API key is needed.

From the root of your repository:

mkdir -p project03/data
curl "https://api.openbrewerydb.org/v1/breweries?per_page=200" -o project03/data/raw_breweries.json

Note the quotes around the URL — without them your shell may swallow the ? and & characters.

What you are getting

Each record looks roughly like this:

{
  "id": "5128df48-79fc-4f0f-8b52-d06be54d0cec",
  "name": "(405) Brewing Co",
  "brewery_type": "micro",
  "address_1": "1716 Topeka St",
  "address_2": null,
  "address_3": null,
  "city": "Norman",
  "state_province": "Oklahoma",
  "postal_code": "73069-8224",
  "country": "United States",
  "longitude": -97.46818222,
  "latitude": 35.25738891,
  "phone": "4058160490",
  "website_url": "http://www.405brewing.com",
  "state": "Oklahoma",
  "street": "1716 Topeka St"
}

Seventeen fields, several of them redundant, and a great many of them null depending on the record. Deciding what to keep and what to do about the gaps is the actual work of this project.

A note on the data changing

Open Brewery DB is community-maintained, so if you download it again next month you may get slightly different records. Download once, commit the file to your repository, and work from that snapshot — which is exactly what a real pipeline does with a source it does not control.

Each script has one responsibility: inspect the source, extract and select fields, transform records in memory, load to CSV, and orchestrate the whole run.

Tasks

Look at the data before you write code against it. Then build the three steps, then wire them together.

Task 0 · inspect – find out what you actually downloaded

Before writing a single line of pipeline code, measure the mess.

Requirements

  • Create scripts/inspect_raw.py inside project03/.
  • Load data/raw_breweries.json and print:
    • How many records you actually received.
    • The full list of keys on the first record.
    • For every field, how many records have it as null or an empty string.
    • The distinct values of brewery_type.
    • How many distinct countries appear.
  • Write what you found into project03-notes.md before continuing.

Hints

  • A dictionary keyed by field name with a count as the value is all you need — the same counting pattern from Project 2.
  • Look closely at latitude, longitude, phone and website_url. The gaps are not evenly spread.
  • Compare state against state_province, and street against address_1. Notice anything?

Task 1 · extract – select and reshape fields

Read the raw JSON and produce a narrower list of records. Selection only — no cleaning yet.

Requirements

  • Create scripts/extract.py inside project03/.
  • Implement extract_breweries(input_path) that:
    • Reads raw_breweries.json using the json module.
    • Returns a list of dictionaries keeping only these fields: id, name, brewery_type, street, city, state_province, country, postal_code, phone, website_url, latitude, longitude.
  • The source has two redundant pairs — state / state_province and street / address_1. Pick one of each and record your reasoning in your notes.
  • Optionally write the result to data/breweries_extracted.json so you can inspect it.

Hints

  • Use .get() rather than [] — not every record has every key.
  • Resist the urge to fix anything here. Nulls stay null, phone numbers stay ugly. Extract selects; transform cleans.

Task 2 · transform – clean, normalize, and decide

The heart of the project. Most of these rules involve a judgment call.

Requirements

  • Create scripts/transform.py.
  • Implement transform_breweries(records), which takes the list from extract_breweries and returns a new list. It must not read or write files, and must not modify the list it was given.
  • Apply at least these rules:
    • Rename state_province to state.
    • name: strip surrounding whitespace and collapse any repeated inner spaces.
    • phone: reduce to digits only, or None when missing or empty.
    • website_url: strip whitespace, lowercase it, remove any trailing slash, or None when missing.
    • postal_code: keep it as a string. For US-style ZIP+4 values like 73069-8224, keep the first five characters.
    • latitude / longitude: keep as numbers, or None.
  • Add these derived fields:
    • has_coordinates — True only when both values are present.
    • is_closed — whether brewery_type is "closed".
  • Decide whether closed breweries belong in your clean output. Either answer is defensible — but write down which you chose and why.

Hints

  • Write one small function per rule and call them in sequence. It is far easier to read, and far easier to change your mind about one rule later.
  • Why keep postal_code as a string? Find a record whose postal code starts with a zero and convert it to int. That is why.
  • Building a new dictionary per record is safer than editing the one you were handed.

Task 3 · load – write clean CSV

Write the cleaned records to a CSV file with a fixed, explicit schema.

Requirements

  • Create scripts/load.py.
  • Implement load_to_csv(records, output_path) that:
    • Uses csv.DictWriter from the standard library.
    • Declares an explicit fieldnames list, for example: ["id", "name", "brewery_type", "street", "city", "state", "country", "postal_code", "phone", "website_url", "latitude", "longitude", "has_coordinates"]
    • Writes a header row, then every record.
  • Open the file with newline="" and encoding="utf-8".
  • Produce project03/data/breweries_clean.csv as the final output.

Verify your output

  • Open the CSV in a spreadsheet. Find a brewery whose street address contains a comma — it must sit in a single column.
  • Find a name with an accent or a non-English character. It must still be readable.
  • Find a postal code that starts with a zero. Is the zero still there?

Hints

  • Let the csv module handle quoting. Never build CSV lines with ",".join(...).
  • DictWriter raises if a record has a key you did not declare. That is a feature — decide deliberately using extrasaction.

Task 4 · pipeline – orchestrate the steps

Wire extract, transform, and load into a single script that runs end to end.

Requirements

  • Create scripts/pipeline.py inside project03/.
  • In a main() function:
    • Set input_path = "project03/data/raw_breweries.json".
    • Set output_path = "project03/data/breweries_clean.csv".
    • Call the steps in order: extract_breweries → transform_breweries → load_to_csv.
    • Print a summary: records read, records written, records dropped, how many are missing coordinates, and where the output file was written.
  • Use if __name__ == "__main__": to run main().
  • Run the pipeline twice in a row. The output must be identical both times.

Optional extension

  • Add argparse so --input and --output can be set from the command line, with the paths above as defaults.

Hints

  • All file reading and writing belongs here and in the load step. The transform step should still know nothing about files.
  • If your summary numbers do not add up — read plus dropped should equal written — that is a bug worth finding.

Stretch · logging, validation, and a quality report

Make the pipeline tell you what it did and what it could not handle.

Optional

Ideas

  • Use the logging module instead of print: log the start and end of each step at INFO, and each rejected record at WARNING.
  • Validate in the transform step: require id, name and country to be present and non-empty. Collect failures into data/breweries_invalid.json rather than discarding them silently.
  • Write a small data quality report — a second CSV, or a section in your notes — giving the percentage of records missing each field.
  • Add filters to the pipeline: --country, --exclude-closed, --require-coordinates.
  • The dataset contains breweries sharing a name at different addresses. Detect them and report how many — but think carefully before "deduplicating" anything.

Reflection and notes

Cleaning data is a series of decisions, not a series of fixes. These questions ask you to defend yours.

Project notes

Create a file project03-notes.md inside project03/ and answer:

  • What did Task 0 tell you that you would not have guessed from looking at one record?
  • How did separating extract, transform, and load affect the way your code is organised?
  • Which normalization rule required the most judgement? What did you decide, and what would somebody who disagreed with you have done instead?
  • What did you do with closed breweries, and with records missing coordinates? Why?
  • If you had to point this pipeline at a completely different JSON dataset, which of your files would change and which would not?

The last question is the real test of whether the three-step split earned its keep.
