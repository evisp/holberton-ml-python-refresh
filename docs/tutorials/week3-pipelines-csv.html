1 Why split one script into three

The conceptual core of the week. Everything else follows from it.

The script that works

You could write the whole project like this, and it would run:

import csv
import json

with open("data/raw_breweries.json") as f:
    raw = json.load(f)

with open("data/clean.csv", "w", newline="") as f:
    writer = csv.writer(f)
    writer.writerow(["id", "name", "city", "country"])

    for record in raw:
        name = record["name"].strip()
        writer.writerow([record["id"], name, record["city"], record["country"]])

Twelve lines, correct output. So why does Project 3 ask for four files instead?

Three questions it cannot answer

  • The source changes to CSV. Now you are editing a file that also contains all your cleaning rules, and you risk breaking them while changing how you read.
  • You need the same cleaning for a different output — a database, JSON, a spreadsheet. The cleaning is tangled up with csv.writer, so you cannot reuse it without copying it.
  • One record produces a wrong value. Where do you look? Reading, cleaning and writing all happen in one loop, so the only way to inspect the middle is to add prints and re-run everything.

The split

Extract, transform, load. It is not tidiness for its own sake — the point is that each kind of change touches exactly one file:

  • extract knows about the source format, and nothing about cleaning.
  • transform knows about your cleaning rules, and nothing about files at all.
  • load knows about the destination format, and nothing about where data came from.
  • pipeline knows the order, and holds the file paths.

Change the source and only extract.py moves. Change the output to a database and only load.py moves. Argue about whether closed breweries belong in the output, and the argument lives entirely in transform.py.

If you saw the intro slides: this is stage two of that diagram, including the arrow that loops back. You will transform, discover something wrong, and return to extract. A split pipeline makes that loop cheap. One long script makes it expensive.

2 Extract – select and reshape

Read the source, keep what you need, hand it on. Nothing else.

Reading is a callback

import json


def extract_breweries(input_path):
    """Read the raw file and return the fields we care about."""
    with open(input_path, encoding="utf-8") as f:
        raw = json.load(f)

    return [select_fields(record) for record in raw]

Note encoding="utf-8". This dataset contains Straße, Södertälje and Fermelã. On some systems the default encoding is not UTF-8 and those records will fail to load — a bug that appears on your classmate's laptop but not yours.

Selecting with .get()

FIELDS = ["id", "name", "brewery_type", "city",
          "state_province", "country", "postal_code",
          "phone", "website_url", "latitude", "longitude"]


def select_fields(record):
    return {field: record.get(field) for field in FIELDS}

A dictionary comprehension over a list of field names. Using .get() means a record missing a key gives None rather than crashing — appropriate here, because at extract time you have not yet decided whether a missing field matters.

The discipline

The temptation is enormous: you are already touching every record, so why not strip the name while you are here? Because the moment extract starts cleaning, you can no longer tell whether a strange value came from the source or from your own code. Keeping extract honest means the intermediate file is a faithful, narrower copy of the source — and that is what makes it useful for debugging.

One decision does belong here: the source carries state and state_province, and street and address_1, holding the same values. Choosing which to keep is selection, not cleaning.

3 The shape of a transform

Data in, data out. No files, no printing, no surprises.

The rule

A transform function takes a value and returns a value. It does not open files, does not print, and does not change anything outside itself. Given the same input it always produces the same output. 

def clean_name(name):
    """Strip the edges and collapse repeated inner spaces."""
    if not name:
        return None
    return " ".join(name.split())

" ".join(name.split()) is a small idiom worth knowing: .split() with no argument splits on any run of whitespace and discards the empties, so joining the pieces back with single spaces normalises the whole string at once.

Why this shape

  • You can test it in the REPL. Call it with a bad value and look at what comes back. No files, no setup.
  • You can reorder or reuse the rules without worrying about hidden effects.
  • Failures are local. If the output is wrong, the bug is inside that one function.

This is Project 1's "return, don't print" rule grown up. There it made your code reusable; here it makes an entire pipeline stage inspectable.

One rule per function, composed

def transform_record(record):
    """Build a new, clean record from a raw one."""
    return {
        "id": record["id"],
        "name": clean_name(record.get("name")),
        "brewery_type": record.get("brewery_type"),
        "city": clean_name(record.get("city")),
        "state": record.get("state_province"),
        "country": record.get("country"),
        "postal_code": clean_postcode(record.get("postal_code")),
        "phone": clean_phone(record.get("phone")),
        "website_url": clean_url(record.get("website_url")),
    }


def transform_breweries(records):
    return [transform_record(record) for record in records]

Notice transform_record builds a new dictionary rather than editing the one it was given. Week 2's aliasing gotcha is why: editing in place would silently change the extracted data too, and then your intermediate file no longer matches what extract produced.

4 What "clean" actually means

Not "repair the broken bits". Cleaning is deciding what your data should look like — and living with it.

Four kinds of cleaning

  • Renaming to a convention — state_province becomes state, because your destination has its own naming rules.
  • Normalizing so that values which mean the same thing look the same.
  • Coercing types so the destination reads them correctly.
  • Deriving fields the source never had, because the destination needs them.

Only the second one is anything like "fixing". The other three are design decisions.

Normalizing a phone number

The same field, across four records in this dataset:

"4058160490"
"+49 9261 628000"
"+32 496 76 40 63"
null
def clean_phone(phone):
    """Reduce a phone number to digits, or None if there isn't one."""
    if not phone:
        return None

    digits = "".join(character for character in phone if character.isdigit())
    return digits or None

This throws away the +. Is that right? It depends what the CSV is for — and that is the point. There is no universally correct answer, only an answer you chose and can defend.

The postal code trap

This dataset contains a brewery in Massachusetts whose postal code is "02351-2419". Watch what happens if you treat it as a number: 

>>> int("02351")
2351

The zero is gone and the postal code is now wrong. Postal codes, phone numbers, and IDs are text that happens to be made of digits — never convert them. Keep them as strings and resist the temptation. 

def clean_postcode(postcode):
    """Keep as text. Reduce US ZIP+4 to the five-digit form."""
    if not postcode:
        return None

    postcode = postcode.strip()

    if "-" in postcode and len(postcode) == 10:
        return postcode[:5]

    return postcode

The length check matters: Portugal uses 3865-127 and Ireland uses R93 X3X8. Splitting on the dash unconditionally would quietly mangle every Portuguese record.

Deriving what the destination needs

def add_derived(record, raw):
    record["has_coordinates"] = (
        raw.get("latitude") is not None and raw.get("longitude") is not None
    )
    record["is_closed"] = raw.get("brewery_type") == "closed"
    return record

has_coordinates did not exist in the source. It exists because whoever reads your CSV wants to filter on it without checking two columns for nulls.

Transform decides the schema

This is the sentence Task 3 depends on. The set of keys coming out of your transform step is your CSV's column list. If the two disagree, the load step will tell you loudly — which is exactly why declaring fieldnames explicitly is worth doing.

Checkpoint 1 · write three cleaning rules

In the REPL, on real values. Ten minutes.

  • Write clean_url(url): strip whitespace, lowercase, drop any trailing slash, return None if empty. Test it on "https://12marias.pt/" and "http://10KBrew.com".
  • Write clean_phone and run it over every record. How many become None?
  • Find a record where clean_postcode does something you did not intend. There is at least one.
  • For each rule, name one person who would reasonably disagree with your choice.

5 CSV, the format

Ten minutes on the format before the module. It prevents a whole class of bugs.

It looks trivial

id,name,city
1,Sample Brewing,Norman
2,Another Brewing,Austin

So why not just build it yourself?

line = ",".join([record["id"], record["name"], record["city"]])

Because of this record

One brewery in the dataset has this street address:

250 Mill St, Suite PW3101

Join that with commas and the row gains a phantom column. Every field after it shifts. Nothing raises an error — the file is simply wrong, and stays wrong until somebody notices a city called Suite PW3101.

Quoting is the answer

The CSV format handles this by wrapping the value in quotes:

id,street,city
abc,"250 Mill St, Suite PW3101",Taylors

And if the value contains a quote, it is doubled. Newlines inside a value work the same way. These rules are fiddly, they have edge cases, and you should never implement them yourself — the csv module already has.

The header row

A header is the schema, written down. Without it, the third column is "whatever the writer happened to put there". With it, the file is self-describing, and pandas will read it in Project 4 without being told anything.

CSV has no types

Everything in a CSV is text. True is written as the five characters T-r-u-e; a spreadsheet may or may not interpret that as a boolean, and different tools disagree. If your consumer needs a number, decide deliberately: write 1 and 0, or write true and false, and document which.

This is also why the leading zero disappears when a spreadsheet opens your file — the tool guesses a type you never asked for. Your CSV is correct; the reader is being helpful.

6 The csv module

Small, standard library, does the fiddly parts correctly.

writer versus DictWriter

csv.writer takes lists, so the column order lives in your head:

import csv

with open("out.csv", "w", newline="", encoding="utf-8") as f:
    writer = csv.writer(f)
    writer.writerow(["id", "name", "city"])
    writer.writerow(["abc", "Sample Brewing", "Norman"])

csv.DictWriter takes dictionaries and you declare the columns once:

FIELDNAMES = ["id", "name", "city", "country", "postal_code"]

with open("out.csv", "w", newline="", encoding="utf-8") as f:
    writer = csv.DictWriter(f, fieldnames=FIELDNAMES)
    writer.writeheader()

    for record in records:
        writer.writerow(record)

Or writer.writerows(records) for the whole list at once. Since your records are already dictionaries, DictWriter is the natural fit — and fieldnames becomes the single place your schema is written down.

newline="" is not optional

The csv module writes its own line endings. If you let Python also translate them, you get a blank line between every row on Windows. It is the single most common CSV bug, it does not reproduce on every machine, and the fix is always the same: 

open(path, "w", newline="", encoding="utf-8")

What DictWriter does about mismatches

  • A key you did not declare raises ValueError by default. Pass extrasaction="ignore" to drop it silently — but do that deliberately, because the error is usually telling you something true.
  • A declared field the record lacks is written as an empty string. Change it with restval="N/A" if you want something else.
  • A None value is written as an empty string. Usually what you want for missing data.

Reading it back

with open("out.csv", newline="", encoding="utf-8") as f:
    for row in csv.DictReader(f):
        print(row["name"], row["postal_code"])

DictReader uses the header row as keys and returns every value as a string — including your numbers and booleans. Project 4 will hand this file to pandas, which does the type guessing for you, and you will finally see why that library exists.

Checkpoint 2 · break a CSV, then fix it

The fastest way to believe any of this.

  • Write five brewery records to a CSV using ",".join(...), including the one whose address contains a comma. Open it in a spreadsheet and find the damage.
  • Write the same five with csv.DictWriter. Confirm the address is one column.
  • Omit newline="" and compare the two files.
  • Read your file back with DictReader and check type(row["latitude"]). Is it what you expected?

7 Orchestrating the steps

One small file that knows the order and holds the paths.

Importing your own modules

from extract import extract_breweries
from transform import transform_breweries
from load import load_to_csv

This works when the four files sit in the same folder and you run pipeline.py from there. If you run it from the repository root instead, Python will not find them — which is the same relative-path lesson from Week 1, now applied to imports rather than data files. Pick one place to run from and stay consistent.

The whole orchestrator

def main():
    input_path = "project03/data/raw_breweries.json"
    output_path = "project03/data/breweries_clean.csv"

    records = extract_breweries(input_path)
    clean = transform_breweries(records)
    load_to_csv(clean, output_path)

    print(f"Read:    {len(records)}")
    print(f"Written: {len(clean)}")
    print(f"Output:  {output_path}")


if __name__ == "__main__":
    main()

Read it aloud and it says what the pipeline does. That readability is the payoff for all the splitting: somebody can understand the shape of the whole thing without opening the other three files.

Where the I/O lives

Paths are here. Reading is in extract, writing is in load, and transform touches no files at all. That boundary is what lets you test your cleaning rules in a REPL without creating a single file.

The guard, for the third time

if __name__ == "__main__": appears in every project so far. Now it has a concrete payoff: extract.py, transform.py and load.py are all imported by pipeline.py. Without the guard, importing them would run whatever sits at the bottom of each.

8 Running it twice

The first project whose output is a file, which brings a question you have not had to ask before.

The same input should give the same output

Run your pipeline twice. The CSV should be identical both times. That property has a name — idempotent — and it is what makes a pipeline safe to re-run when something upstream changes.

Opening with "w" gives you this for free: the file is truncated and rewritten from scratch. Opening with "a" appends, so a second run doubles your data and a third triples it. For a pipeline output, "w" is almost always correct. 

python3 project03/scripts/pipeline.py
wc -l project03/data/breweries_clean.csv

python3 project03/scripts/pipeline.py
wc -l project03/data/breweries_clean.csv    # must be the same number

Things that quietly break it

  • Appending instead of overwriting.
  • Putting a timestamp in the output — now no two runs match.
  • Iterating a set and writing rows in its order, which is not guaranteed. Sort first.

What the intermediate file is for

Project 3 offers an optional breweries_extracted.json between the steps. It is not required, and it is genuinely useful: it lets you look at the middle of the pipeline without re-running the start. When your CSV has a wrong value, you can answer "did extract produce this, or did transform?" by opening one file.

On a small dataset that is a convenience. On a pipeline whose extract step takes twenty minutes, it is the difference between a two-minute debug and an hour of waiting.

9 When records are bad

Missing values are normal. Deciding what to do about them is your job, not the data's.

Three responses, and when each is right

  • Fill it. Write an empty string or a default. Right when the field is optional and its absence is not interesting.
  • Flag it. Keep the record, add a field like has_coordinates. Right when the consumer should decide.
  • Drop it. Exclude the record and count it. Right only when the record is unusable — no id, no name.

The wrong response is to crash. A quarter of this dataset is missing coordinates; a pipeline that stops on the first one is useless.

Validate at the boundary

def is_valid(record):
    """A record we can actually use."""
    return bool(record.get("id")) and bool(record.get("name"))


def transform_breweries(records):
    clean = []
    rejected = []

    for record in records:
        if not is_valid(record):
            rejected.append(record)
            continue
        clean.append(transform_record(record))

    return clean, rejected

Check once, at the entrance to the transform step, and everything downstream can assume good input. The alternative — defensive checks scattered through every function — is how code becomes unreadable.

Note that rejected is returned, not printed. The transform step reports what it could not handle; the orchestrator decides whether to log it, save it, or ignore it.

Logging beats printing

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)-8s %(message)s",
)

logging.info("Extracted %d records", len(records))
logging.warning("Rejected %d records with no id or name", len(rejected))

Three things print cannot do: attach a severity so you can silence the chatter without losing the warnings, timestamp every line, and redirect to a file without touching your code. For anything that runs unattended, that matters.

Note the comma before len(records) rather than an f-string. Logging only formats the message if that level is actually enabled — a small habit worth picking up early.

10 Putting it together

A complete pipeline on a different dataset — the books from Week 1, now as JSON.

The input: raw_books.json

[
  {"title": "  The Hobbit ", "author": "Tolkien", "pages": 310, "isbn": "0345339681"},
  {"title": "Dune", "author": "Herbert", "pages": null, "isbn": "0441013597"},
  {"title": "Sula", "author": null, "pages": 174, "isbn": "0452283868"},
  {"title": "", "author": "Unknown", "pages": 200, "isbn": "0000000000"}
]

extract.py

import json

FIELDS = ["title", "author", "pages", "isbn"]


def extract_books(input_path):
    """Read the raw file and keep only the fields we need."""
    with open(input_path, encoding="utf-8") as f:
        raw = json.load(f)

    return [{field: record.get(field) for field in FIELDS} for record in raw]

transform.py

def clean_text(value):
    """Strip and collapse whitespace, or None if there is nothing left."""
    if not value:
        return None
    cleaned = " ".join(value.split())
    return cleaned or None


def is_valid(record):
    """We can live without an author. We cannot live without a title."""
    return bool(clean_text(record.get("title")))


def transform_record(record):
    title = clean_text(record.get("title"))
    pages = record.get("pages")

    return {
        "title": title,
        "author": clean_text(record.get("author")) or "Unknown",
        "pages": pages,
        "has_page_count": pages is not None,
        "isbn": record.get("isbn"),          # text, never an int
        "title_length": len(title),
    }


def transform_books(records):
    """Return (clean, rejected). No files are touched here."""
    clean = []
    rejected = []

    for record in records:
        if is_valid(record):
            clean.append(transform_record(record))
        else:
            rejected.append(record)

    return clean, rejected

load.py

import csv

FIELDNAMES = ["title", "author", "pages", "has_page_count", "isbn", "title_length"]


def load_to_csv(records, output_path):
    """Write records to CSV using an explicit schema."""
    with open(output_path, "w", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=FIELDNAMES)
        writer.writeheader()
        writer.writerows(records)

pipeline.py

import logging

from extract import extract_books
from transform import transform_books
from load import load_to_csv

logging.basicConfig(level=logging.INFO, format="%(levelname)-8s %(message)s")


def main():
    input_path = "data/raw_books.json"
    output_path = "data/books_clean.csv"

    records = extract_books(input_path)
    logging.info("Extracted %d records", len(records))

    clean, rejected = transform_books(records)
    if rejected:
        logging.warning("Rejected %d records with no usable title", len(rejected))

    load_to_csv(clean, output_path)

    print(f"Read:     {len(records)}")
    print(f"Written:  {len(clean)}")
    print(f"Rejected: {len(rejected)}")
    print(f"Output:   {output_path}")


if __name__ == "__main__":
    main()

What it produces

title,author,pages,has_page_count,isbn,title_length
The Hobbit,Tolkien,310,True,0345339681,10
Dune,Herbert,,False,0441013597,4
Sula,Unknown,174,True,0452283868,4

What to notice

  • Four records in, three out, one rejected — and the count is reported rather than hidden.
  • The missing pages value became an empty CSV cell, with has_page_count saying so explicitly.
  • The missing author became "Unknown" — a different decision for a different field, deliberately.
  • The ISBN kept its leading zero because it was never converted to a number.
  • transform.py imports nothing. It has no idea where the data came from or where it is going.

11 Gotchas

Six things that will cost you an evening if you meet them cold.

Forgetting newline=""

Blank lines between every row, on some machines only. Always pass it when opening a file for the csv module.

Converting things that only look like numbers

Postal codes, phone numbers, ISBNs, IDs, and anything with a leading zero. If you will never do arithmetic on it, it is text.

Trusting dictionary order instead of fieldnames

DictWriter writes columns in the order you declared, not the order your dictionary happens to have. That is a feature — but it means adding a key in transform and forgetting to declare it in load will raise, and rightly so.

Mutating the input list

def transform(records):
    for record in records:
        record["name"] = clean_name(record["name"])   # changes the caller's data
    return records

Build and return new dictionaries instead. Week 2's aliasing lesson, with higher stakes.

Encoding

Pass encoding="utf-8" when reading and writing. Without it Python uses a platform-dependent default, and a file that works for you fails for somebody else.

Running from the wrong folder

Relative paths for data, and imports between your own scripts, both depend on where you launched Python. Decide once whether you run from the repository root or from project03/scripts/, and write it at the top of your notes.
