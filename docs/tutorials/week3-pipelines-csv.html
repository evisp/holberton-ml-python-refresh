Week 3 tutorial

The shape of a pipeline

A short orientation, not a manual. Read this to understand the data you are about to clean and the four stages you are about to build. The work itself happens in Project 3.

Reading time: 10 minutes Assumes: Weeks 1–2 Prepares you for: Project 3
Meet the data Go to Project 3

1 The data

Open Brewery DB: breweries, cideries and brewpubs from around the world, maintained by volunteers. It is real, and real data is never tidy.

Two records from the same file

Here is a complete one:

{
  "name": "(405) Brewing Co",
  "city": "Norman",
  "postal_code": "73069-8224",
  "country": "United States",
  "latitude": 35.25738891,
  "phone": "4058160490",
  "website_url": "http://www.405brewing.com"
}

And here is another, from the same download:

{
  "name": "12 Marias",
  "city": "Estarreja",
  "postal_code": "3865-127",
  "country": "Portugal",
  "latitude": null,
  "phone": null,
  "website_url": "https://12marias.pt/"
}

Same schema, entirely different content. Neither record is broken. Both are just real — and your pipeline has to survive both without being told which is which.

The gaps

Around a quarter of records have no coordinates. Others are missing a phone, a website, or even a street address. Nothing is uniformly absent, so you cannot simply drop a column.

The formats

The same field, four ways: 4058160490, +49 9261 628000, +32 496 76 40 63, 353599107299. All valid. None comparable.

The traps

A postal code of 02351-2419 that loses its zero if you treat it as a number. An address reading 250 Mill St, Suite PW3101 that breaks a naive CSV. A brewery called 1516 Westparkbräu that breaks careless encoding.

The repeats

10 Barrel Brewing Co appears four times — four different addresses, four different ids. Duplicates by name, genuinely distinct by record. Deciding what that means is your call, not the data's.

Why this matters more than it looks

In Weeks 1 and 2 the data was clean, so the only question was how do I write this. Here the data has opinions, and the interesting question becomes what should this look like when I am done. That is a design question, and it has more than one defensible answer.

2 The pipeline at a glance

Four stages, each a separate file, each with one job. If you remember one thing from this page, make it this.

Step 0

Inspect

Find out what you actually have, before writing code against it.

Step 1

Extract

Read the source and keep the fields you need. Nothing else.

Step 2

Transform

Decide what the data should look like, and make it look like that.

Step 3

Load

Write it out in the format the next tool expects.

It is not a straight line

You will reach Transform, discover a field you assumed was always present is missing on a fifth of records, and go back to Inspect. That loop is normal — it is the reason the stages are separate files. Going back should cost you one file, not the whole program.

Inspect

Goal: replace your assumptions about the data with measurements.

What this stage is for

Everyone looks at the first record and starts coding. The first record is never representative. Count the missing values per field, list the categories, and check whether the fields you plan to rely on are actually always there.

What it looks like on this data

latitude          62   31.0%  #######
longitude         62   31.0%  #######
phone             34   17.0%  ####
website_url       31   15.5%  ###
street             5    2.5%  #

Five minutes of counting tells you that a pipeline which requires coordinates would throw away a third of the dataset. That changes what you build, and you could not have guessed it.

You got it wrong if…

…you find yourself surprised halfway through Transform. Surprise at that stage means the inspection was too shallow.

Extract

Goal: get the data out of its source format and down to the fields you care about.

Belongs here

  • Opening the file and parsing the JSON.
  • Choosing which of the seventeen fields to keep.
  • Choosing between the redundant pairs — the source carries both state and state_province, and both street and address_1, holding identical values.

Does not belong here

  • Stripping whitespace. Fixing phone numbers. Filling in blanks.
  • Anything that changes a value rather than choosing it.

Why so strict

The temptation is real: you are already touching every record, so why not tidy up while you are here? Because the moment Extract starts cleaning, you can no longer tell whether a strange value came from the source or from your own code. Keeping Extract honest means its output is a faithful, narrower copy of the original — and that is what makes it useful when something goes wrong.

You got it wrong if…

…changing the source from JSON to CSV would mean editing your cleaning rules.

Transform

Goal: decide what your data should look like — then make every record look like that.

Four kinds of cleaning

Only one of them is really "fixing". The rest are decisions.

  • Rename to a convention. state_province becomes state, because your output has its own naming rules.
  • Normalize so values that mean the same thing look the same.
  • Coerce types so the destination reads them correctly.
  • Derive fields the source never had, because the consumer needs them.

What that looks like on this data

phone          "+49 9261 628000"    →  "499261628000"
website_url    "http://10KBrew.com" →  "http://10kbrew.com"
postal_code    "73069-8224"         →  "73069"
name           "  Double   Spaced " →  "Double Spaced"

has_coordinates      (did not exist) →  True / False

Each of those arrows is a choice you made. Reducing the phone to digits throws away the leading +, and with it the country-code marker. Is that right? It depends what the file is for — which is exactly the point.

The one rule that is not a judgement call

Never convert something to a number just because it looks like one. A postal code of 02351 becomes 2351 and is now simply wrong. Postal codes, phone numbers, IDs and ISBNs are text that happens to be made of digits. If you will never do arithmetic on it, it stays a string.

Missing values: fill, flag, or drop

  • Fill when the field is optional and its absence is uninteresting.
  • Flag — keep the record, add has_coordinates — when the consumer should decide.
  • Drop only when the record is genuinely unusable, and always count how many.

The wrong answer is to crash. A third of this dataset has no coordinates; a pipeline that stops at the first one is useless.

Keep this stage pure

Transform should take data and return data. No opening files, no printing, no changing the list it was handed. That is what lets you test a single rule in the REPL without creating anything — and it is Project 1's "return, don't print" rule, grown up.

You got it wrong if…

…you cannot explain, for any given rule, what someone who disagreed with you would have done instead.

Load

Goal: write the result in a format the next tool can read — correctly, every time.

The column list is the contract

Declare your columns explicitly and in order. That list is your schema, written down in one place. If Transform starts producing a field Load does not know about, you want to hear about it immediately rather than discover a missing column next week.

Why you must not build CSV by hand

One brewery in this dataset has the street address 250 Mill St, Suite PW3101.

joined by hand:   abc,13 Stripes Brewery,250 Mill St, Suite PW3101,Taylors
                                                          ↑ a column appeared

written properly: abc,13 Stripes Brewery,"250 Mill St, Suite PW3101",Taylors

Nothing raises an error in the first case. The file is simply wrong, every column after the address has shifted, and nobody notices until a city called Suite PW3101 turns up in Project 4. Quoting is the answer, and Python's csv module already implements it — correctly, including the awkward cases you would forget.

A CSV has no types

Everything in the file is text. True is five characters. 35.25 is five characters. When you read it back, everything arrives as a string — which is exactly why pandas exists, and why you will meet it in Project 4.

You got it wrong if…

…your accented brewery names came out as mojibake, your leading zero vanished, or there is a blank line between every row. All three are one-argument fixes, and all three are in the card below.

Go deeper · the three arguments that prevent three bugs

Short, specific, and each one will bite you at least once.

  • newline="" when opening the file. The csv module writes its own line endings; without this you get a blank line between every row on Windows. It does not reproduce on every machine, which is what makes it maddening.
  • encoding="utf-8" when reading and writing. Without it Python picks a platform default, and Straße survives on your laptop but not on your classmate's.
  • Postal codes as strings, all the way through. The zero disappears at whichever point you convert — and a spreadsheet opening your file may helpfully convert it for you, which is worth knowing before you blame your own code.

3 Why four files instead of one

You could write all of this as one thirty-line script, and it would work. Here is what it could not do.

Three questions a single script answers badly

  • The source changes to CSV. Now you are editing a file that also contains every cleaning rule, and risking them while you work.
  • You need the same cleaning for a different output. It is tangled up with the writing, so you copy it — and now there are two versions to keep in step.
  • One value comes out wrong. Reading, cleaning and writing all happen in one loop, so the only way to see the middle is to add prints and re-run everything.

What each file owns

  • extract — the source format. Knows nothing about cleaning.
  • transform — your rules. Knows nothing about files at all.
  • load — the destination format. Knows nothing about where the data came from.
  • pipeline — the order, and the paths. Knows nothing about the data.

The payoff is that each kind of change touches exactly one file. That is the whole argument, and it is worth more than it sounds: it is the difference between a script you throw away and one you can still use in six months.

Go deeper · running it twice, and saying what happened

Two habits that separate a script from a pipeline.

  • The same input should always give the same output. Run your pipeline twice and compare the files — they must be identical. Opening with "w" gives you this; "a" quietly doubles your data on the second run.
  • Report, do not hide. Print how many records were read, written and skipped. If read minus skipped does not equal written, you have a bug worth finding.
  • Use logging rather than print once the pipeline runs unattended. It gives you severity levels, timestamps, and the ability to send output to a file without touching your code.
  • The optional intermediate file earns its keep when something is wrong: it lets you answer "did Extract produce this, or did Transform?" by opening one file instead of re-running everything.

4 Before you start

You are ready for Project 3 when you can answer these out loud.

Self-check

  • Name three ways this dataset is messier than the todos from Project 2.
  • Say what each of the four stages is for, in one sentence each.
  • Give a concrete reason to split a working script into separate files.
  • Say what belongs in Extract and what does not.
  • Name the four kinds of cleaning, and which one is not really "fixing".
  • Explain why a postal code must never become an int.
  • Say what happens when a value contains a comma, and who solves it.
  • Choose between filling, flagging and dropping a missing value — and defend the choice.

Anything you hesitated on: reread that section. Everything else you will learn faster by building it.
